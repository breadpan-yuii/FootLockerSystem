10 - USE CASE DIAGRAMS - MASTER INDEX + USE-CASE REGISTRY
========================================================================
This folder now documents the THREE use case diagrams using PROPER UML
use case notation (actor stick figures OUTSIDE a subject rectangle named
"Foot Locker PH System", goals as ellipses INSIDE, plain associations
with no arrowheads).

The three figures are produced from three separate, self-contained guide
files (one per actor), as required by 15_Formatting_Specs.txt:
    02a Guest     -> docu/10a_Use_Case_Guest.txt     (6 use cases)
    02b Customer  -> docu/10b_Use_Case_Customer.txt  (10 use cases)
    02c Admin     -> docu/10c_Use_Case_Admin.txt     (12 use cases)

Master source of truth: routes/web.php (lines 18-68) + routes/auth.php +
app/Http/Controllers/*. Every use case maps to a real route; nothing is
invented. Email verification routes exist (auth.php 39-47) but the flow
is DORMANT in the code (User does not implement MustVerifyEmail, no
"verified" middleware), so it is excluded from every figure.

------------------------------------------------------------------------
NOTATION CONVENTIONS (apply to all three figures)
------------------------------------------------------------------------
- SUBJECT: one rectangle labeled "Foot Locker PH System"; all ellipses
  inside; actors outside.
- ACTOR: stick figure. Guest/Customer drawn on the LEFT, Admin on the
  RIGHT. One actor per figure (02a/02b/02c are per-user figures).
- ASSOCIATION: plain solid line, NO arrowhead (actor <-> use case).
- «include»: DASHED arrow with open arrowhead, FROM the base use case TO
  the included use case. Means the included behaviour ALWAYS happens.
- «extend»: DASHED arrow with open arrowhead, FROM the extending use case
  TO the base use case. Means OPTIONAL/conditional behaviour.
- No generalisation between actors or use cases; no flowchart arrows.
  (Refs: uml-diagrams.org/use-case-reference.html; swebook.org §5.)

------------------------------------------------------------------------
USE-CASE RELATIONSHIPS (only genuinely applicable ones)
------------------------------------------------------------------------
  UC21 Update Order Status  «include»  UC20 View Order Details   (Figure 02c)
      Reason: the status form is rendered on the order-detail page
      (admin/orders/show.blade.php:43), so viewing details ALWAYS occurs.

  UC19 Delete Account       «extend»   UC9 Manage Profile        (02b and 02c)
      Reason: deleting is optional and password-confirmed; Manage Profile
      is complete without it.

  Deliberately NOT modeled:
      - "Log In includes ..." / "... includes Log In": authentication is a
        session PRECONDITION, not a step inside each goal (Cockburn).
      - Checkout/payment sub-steps: internal system behaviour, not actor
        goals (a use case diagram is an index, not a flowchart).
      - Product variants/images as includes: those inputs are NULLABLE in
        Admin\ProductController validation, so they are not mandatory.
